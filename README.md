# Introduction

This is a beginner-level verification project where I built a basic UVM testbench for a Verilog D Flip-Flop.

The main goal of this project was to gain introductory exposure to SystemVerilog and understand the structure of a UVM verification environment.

---

# Project Overview

The Design Under Test (DUT) is a simple D Flip-Flop written in Verilog.

A UVM-based testbench was created to verify the clocked behavior of the D Flip-Flop by comparing the expected output with the actual output.

The top-most layer of the testbench.

Responsibilities:

- Clock generation
- DUT instantiation

### Interface

Connects the DUT and testbench components.

---

### Test Environment

The test environment contains:

- Agent
- Scoreboard

#### Agent

The Agent contains:

- Driver
- Sequencer
- Monitor

##### Driver

Drives transactions to the DUT through the interface.

##### Sequencer

Sequences generated transactions and sends them to the Driver.

##### Transaction / Sequence Item

Generated by the Sequence.

##### Monitor

Collects results from the DUT and sends them to the Scoreboard.

#### Scoreboard

Determines whether the test passes or fails.

---
### UVM Objects

- Sequence Item
- Sequence

These are UVM Objects because they are dynamic in nature and are destroyed at the end of simulation.

They do **not** contain UVM phases.

### UVM Components

- Test
- Environment
- Agent
- Driver
- Sequencer
- Monitor
- Scoreboard

These remain present during and after simulation and participate in UVM phases.

All phases are functions and execute hierarchically starting from the Test and propagating downward.

# Build Phase

The Build Phase is responsible for instantiating and constructing lower-level components.

Two methods can be used:

1. `new()`
2. `type_id::create()`

This project uses:

```systemverilog
type_id::create()
```

If a component has no sub-components, it does not need to instantiate anything separately during the Build Phase.

<img width="910" height="555" alt="image" src="https://github.com/user-attachments/assets/5bd7f602-ab83-49d1-a262-c5e2bc7521cb" />

### Passing Interface using uvm_config_db

The interface is set inside the top module using `uvm_config_db` so that it can be accessed inside the Driver and Monitor.

If the Driver cannot receive the interface correctly, a `uvm_fatal` message is generated.

# Connect Phase

### Transaction-Level Modeling (TLM)

Instead of communicating bit-by-bit, UVM communicates using complete transactions or packets.

## Inside Agent

Communication between the Sequencer and Driver uses a regular TLM port.

- Driver (receiver): `seq_item_port`
- Sequencer (sender): `seq_item_export`

<img width="605" height="130" alt="image" src="https://github.com/user-attachments/assets/b7958ddd-b124-49a2-9aeb-6cc6a6558d41" />

## Inside Environment

Communication between the Monitor and Scoreboard uses a TLM Analysis Port.

Inside the Monitor:

- Instantiate `uvm_analysis_port`
- Connect it to `item_collected_port`

Inside the Scoreboard:

- Instantiate `item_collected_export`
- Use `uvm_analysis_imp`
- Create it using the `new()` method

These ports are connected inside the Environment.

# Run Phase

The Run Phase is a task.

It is the heart of simulation because all transaction flow occurs here and it consumes the majority of simulation time.

The Monitor's `item_collected_port` is connected to the Scoreboard's `item_collected_export`.

Therefore, both the Agent and Environment require Connect Phases.

## Run phase in Test

The test must remain in the Run Phase until the test class drops its objection.

This provides sufficient time for sequence execution.

```systemverilog
phase.raise_objection(this);

seq.start(env.agent.seqr);

phase.drop_objection(this);
```

## Run phase in Environment

A separate Run Phase is not required for the Environment in this project.

## Run phase in  Driver

<img width="476" height="277" alt="image" src="https://github.com/user-attachments/assets/d0b588e2-2435-41e4-be11-4c4ffcc2fbc1" />

The Driver:

1. Receives transactions using `get_next_item()` through `seq_item_port`.
2. Drives the transaction using a custom task called `drive()`.
3. Sends `seq_item_port.item_done()` after completion.

The transaction consists of:

- rst
- d
- q

The interface signals `rst`, `d`, and `q` are driven using the corresponding transaction values.

<img width="1086" height="797" alt="image" src="https://github.com/user-attachments/assets/50384196-7da7-4a3c-a3d4-28c38d4aed0b" />

*Sequence → Sequencer → Driver communication during the Run Phase.*

## in Sequence

Since Sequence is a UVM Object, it does not contain phases.

Instead, functionality is implemented inside the `body()` task.

Process:

1. Create transaction using `type_id::create()`
2. Request grant using `wait_for_grant()`
3. Randomize transaction
4. Send transaction to Sequencer
5. Wait for `item_done()` from Driver
6. Repeat

For example, the repeat count can be set to 5 to generate five randomized transactions.

<img width="352" height="208" alt="image" src="https://github.com/user-attachments/assets/04e8e265-caae-4ecb-a743-11b3efde550c" />

## Run phase in Monitor

At every positive edge of the clock, the Monitor samples interface signals and combines them into a new transaction.

<img width="402" height="193" alt="image" src="https://github.com/user-attachments/assets/faaa1ebb-eb93-4abf-aabe-0c2a8e501e56" />

## Run phase in Scoreboard

All received transactions are stored in a queue (`tx_q`) using the `write()` function.

<img width="662" height="107" alt="image" src="https://github.com/user-attachments/assets/00dc89cf-8fb2-43d3-8238-7107158a8e2e" />

Transactions are popped one at a time from the queue.

Checking logic:

- If D = Q → PASS
- Else → FAIL

# Constraints

- Reset is constrained to remain 0 at all times.
- D is randomized.

# Design Under Test

The D Flip-Flop captures the input `d` on the active clock edge and updates the output `q`.
